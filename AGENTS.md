## Правила работы с владельцем

- **Изменения отдаются одним патчем для `git am`** поверх текущего `master`
  `github.com/unxed/go2dos`. Клонировать репозиторий заново прямо перед экспортом
  патча (владелец мог влить предыдущий), включать только то, чего в `master`
  ещё нет, проверить `git am` на свежем клоне и назвать целевой репозиторий.
  Двоичные файлы (`.com`) — только с `.gitattributes` `binary`, иначе `git am`
  срезает CR и портит их.
- **Полные наборы тестов гоняет GitHub CI**, не сессия. Локально — то, без чего
  не обойтись в разработке (запуск VC при расследовании, сборка).
- **ГАДАТЬ ЗАПРЕЩЕНО.** Не выдавать догадку за диагноз и не чинить
  неустановленную причину. Сначала исчерпать читаемые источники: исходники VC
  (`github.com/ddanila/vc`), трассу go2dos, дамп, документацию (RBIL). Если
  причина не установлена — так и сказать и добавить инструментирование. Факты
  отделять от гипотез (в `DOUBTS.md` — пометки «установлено»/«предположение»).
- **Сложная отладка — протокол чёрного ящика:** на каждом шаге ответить на три
  вопроса: что узнали на прошлом шаге, чего ещё не знаем, как это узнать. Код
  пишется только для сбора информации; к починке — когда владелец объявит
  расследование законченным.
- **RUP:** самое простое сначала, мелкие шаги, проверка на живой программе (VC).
- **Решения по дизайну и инструментам принимать самому**, информацию собирать
  самому, а не спрашивать владельца. Документированные интерфейсы лучше
  обратной разработки.
- **Инструкции для машины владельца** — один блок для вставки в терминал, который
  сам печатает подсказки; перед сложной инструкцией — «прочитайте до конца».
- **Windows** — сначала GitHub CI и Wine; ноутбук с Windows — только для
  финальной проверки.
- Библиотеки: документацию сверять через Context7 (знает `/golang/term`,
  `/unxed/localecp`; `x/text/encoding/charmap` там не находится — сверять по
  исходникам модуля в `$(go env GOMODCACHE)`), иначе — веб-поиск.

## Окружение

```sh
go version                      # не ниже указанного в go.mod
sudo apt-get install nasm       # testdata/progs и ndisasm для дампов
sh tools/fetch-vc.sh .cache/vc  # VC 4.05 и 4.99.09 (BSD-2), с проверкой SHA-256
sh tools/fetch-sst.sh .cache/sst  # SingleStepTests 8088 v2, около 600 МБ
```

Готовые бинарники VC берутся из релиза `latest-build` репозитория `ddanila/vc`
(страница `releases/expanded_assets/latest-build`; REST API GitHub без токена
быстро упирается в лимит). Исходники VC: `versions/4.05`, `versions/4.99.09`
в том же репозитории; ветка `build` — сборка (TASM в QEMU, JWasm для 4.99.09)
и e2e-тесты.

## Правила для агентов (по итогам разбора 01-10-2026)

go2dos — эмулятор DOS на **Go**. Проект m5 (клон Midnight Commander) — отдельный репозиторий на Rust, его код сюда не кладётся.

1. Каждый проект — только свои репозитории. PR и ветки в чужих репозиториях (f4, vtui, localecp и др.) запрещены без слова владельца. m5 — Rust, go2dos — Go; код одного проекта не кладётся в другой.
2. Готовый PR (CI зелёный) мержится немедленно, в ту же минуту, как стал готов. Ждать, пока накопятся другие, запрещено; копить открытые PR нельзя ни под каким предлогом. Если на момент проверки уже готовы несколько PR — мержи их все подряд сразу, не дожидаясь CI между слияниями; это порядок слияния уже готовых, а не отсрочка. Красный CI чинить, а не оставлять. Брошенные ветки и дубли удалять сразу после слияния или закрытия PR.
3. Никаких `-X theirs` / `-X ours` при ребейзе и слиянии (молча теряют изменения): конфликты разбирать по смыслу. Никаких `git push -f` в общие ветки; `main` не переписывать.
4. Не заводить собственных «тикетов вопросов и прогресса». Вопросы владельцу — только в unxed/lunobot#29 через `notify_owner.py` и только такие, которые нельзя решить самому. Прогресс — коммитами и статус-файлами.
5. Отчёты — только о проверенном по факту (`gh pr`, `gh run`, дерево файлов): без выдуманных чисел, тестов и «готово». В документации не утверждать непроверенное; факты отделять от гипотез.
6. Не вести параллельно две реализации одной задачи: перед началом проверить открытые PR и `main` на дубли.
7. Проприетарные бинарники (NC, игры) не коммитить: только fetch-скрипты с SHA-256; тесты без бинарника честно пропускаются (`t.Skip` / skip с понятным сообщением).
8. Каждое поручение владельца выполнять буквально и только его, ничего не расширять.

## Карта кода

- `cpu/` — интерпретатор. Ловушка HLE — `FE 38 lo hi`. `cpu.ErrRetry` из
  обработчика — повторить инструкцию позже с IF=1 (ожидание ввода).
- `hle/` — реестр обработчиков (`Env.HookInt`, `Register`, `Emit`), флаги
  результата — только через `e.SetCF/SetZF` (в стековом кадре), пояснение в
  трассу — `e.Note`, неподдерживаемое — `hle.Unsupported(...)` (fail fast).
- `bios/` — `video.go` (INT 10h, CRTC, модель 3DAh, `Snapshot`), `bios.go`
  (клавиатура через порт 60h/IRQ1, INT 16h/08h/1Ah/15h/33h).
- `dos/` — `int21.go` (диспетчер), `fs.go` (пути, 8.3, алиасы), `files.go`
  (хэндлы, поиск), `exec.go` (EXEC), `console.go`, `dos.go` (MCB, загрузчик).
- `machine/` — цикл исполнения, PIC/PIT, порты, простой, `Dump`, `RunScript`.
- `keys/` — имена клавиш, скрипты (`<waitfor:…>`, `<wait:…>`, `<screen>`).
- `cmd/go2dos/` — терминальный фронтенд и headless.

Политика ответов: неизвестная функция — fail fast; проверки наличия
(`INT 2Fh`, `INT 10h/FEh` и т.п.) — регистры без изменений = «не установлено»;
порты без устройства — `FFh` и запись в трассу.

## Как расследовать

```sh
go build -o /tmp/go2dos ./cmd/go2dos
cd .cache/vc/4.99.09
/tmp/go2dos -headless -timeout 5s -trace /tmp/t.jsonl -trace-filter int21 \
  -dump-on-exit -dump-dir /tmp ./VC.COM
/tmp/go2dos -headless -timeout 5s -trace /tmp/w.jsonl -trace-filter port \
  -watch 22CD ./VC.COM            # кто пишет по линейному адресу
/tmp/go2dos -headless -timeout 5s -trace /tmp/b.jsonl -trace-filter port \
  -break 0156:0361 ./VC.COM       # регистры в момент исполнения адреса
ndisasm -b16 -o0xOFF -e$((0xSEG*16+0xOFF)) /tmp/go2dos-dump-*/memory.bin | head
```

В дампе: `report.txt` (регистры, байты по CS:IP, стек, последние HLE-вызовы и
адреса исполнения), `memory.bin`, `screen.txt`, `trace.jsonl`, `keys.txt`.

## Состояние и следующие шаги (по приоритету)

Рабочая очередь с уровнями сложности и стоп-условиями — `docs/TASKS.md`.
Младшая модель берёт только задачи уровня H. Список ниже — общий порядок.

1. VC 4.05 и 4.99.09 работают (e2e). Дальше — очередь `docs/TASKS.md`.
2. LFN (`INT 21h/71xx`) в эмуляторе — сейчас ответ «не поддерживается».
3. Буфер обмена: WinOldAp (`INT 2Fh/17xx`) в HLE, копирование с экрана и
   вставка нажатиями во фронтенде (DESIGN §9).
4. Фронтенд на `vtui` (полноценные события клавиш, буфер обмена хоста).
5. `third_party/vc`: сопровождаемая сборка VC с буфером обмена, LFN для 4.05,
   UTF-8 именами (DESIGN §18).
6. Провайдер UTF-8 имён (`docs/UTF8NAMES.md`) и клиент в VC.
7. `COMMAND.COM` (FreeCOM) для командной строки VC/NC.
8. Экран (M10b): окно любого размера, режим консоли хоста, склейка длинных
   строк (`docs/SCREEN.md`). Ключ — разделить поток (телетайп) и сетку
   (видеопамять).
8a. Мост DOS → WASI (M11): `docs/WASI-BRIDGE.md` — решение, архитектура,
   план W0–W7. Исследование R1–R5 можно делать в любой момент, реализацию —
   после UTF-8 имён (M10). UTF-8 имена мостом не заменять.
9. go2dos под wasm-рантаймом и в браузере (M12).
   Затем трансляция x86 → wasm (M13): один транслятор для JIT и AOT, откат
   на интерпретатор, метаданные JWasm и покрытие как источники блоков
   (`docs/TRANSLATION.md`). Бэкенд wasm в JWasm не писать.
10. Дальние планы: Dos Navigator, Norton Commander (DESIGN §20). Для DN —
    сначала аудит кода Turbo Vision, переработка и двойная перепроверка, затем
    вынос TV в отдельный проект (`docs/DN-PLAN.md`). Код TV и DN не попадает
    в репозитории.
11. В самом конце: HX DOS Extender — его Win32-слой (имена `...W`, буфер
    обмена) через наши API, чтобы Win32-программы под HX (например, Far)
    получили UTF-8 имена и буфер обмена хоста (DESIGN §20, п. 3). Требует 386,
    защищённого режима и DPMI в go2dos. Форк — `github.com/unxed/HX`, у токена
    агента есть права на запись; изменения HX вносятся туда.

## Грабли, на которые уже наступили

- `printf '\x1d'` в `sh` (dash) печатает буквально — нужны восьмеричные
  `\035`, `\033`.
- Фоновые процессы в песочнице могут умирать вместе с командой, превысившей
  лимит времени: запускать через `setsid nohup`, загрузки делать докачиваемыми.
- `localecp` на Windows: `OEMEncoding` верен только для 866, номер
  `OEMCodepage` — всегда (подробности в `DOUBTS.md`).
- Тестовые сценарии ждут текста на экране, а не времени: `<waitfor:…>` вместо
  пауз (опыт cpmulator, DESIGN §17). Учти, что `<waitfor:C:\>` срабатывает и
  на сообщениях вроде `C:\VC.INI` — ждать лучше уникальный текст (`10Quit`).

## Состояние на 01-10-2026 (зафиксировано при остановке воркеров)

Сделано и подтверждено CI на main: объяснение «одной панели» (VC без VC.INI выключает левую панель, Ctrl-F1 включает, Shift-F9 сохраняет VC.INI) с регрессионными тестами; NC 5.51 и DN 1.51 запускаются без `-lenient` (fetch-скрипты, джоб `e2e-nc-dn`); API DOS-HOST/TEXTWIN.
Начато и НЕ закончено: UTF-8 имена файлов в Volkov Commander (приоритет владельца: ни одна операция с файлами — переименование, копирование, перемещение, удаление — не должна терять символы UTF-8; на экране то, что не влезает в кодовую страницу, можно показывать «?»; в main не влито ни кода, ни тестов, способ не выбран; вариант (а) обратимое кодирование имён внутри DOS-видимой строки, вариант (б) сборка VC с клиентом UTF-8 имён через провайдер DOS-UTF8/NAMES).
Не начато: режим конвейера (stdin/stdout), копирование с экрана и вставка в DOS-программу, UTF-8 перекодировка для DOS-программ через localecp и UTF-8 буфер обмена. Причина NC с одной панелью без NC.INI не исследована; просмотр, редактор, копирование и мышь в NC и DN не проверялись.
