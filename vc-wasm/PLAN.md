# vc-wasm: план для исполнителя

Для модели, которая продолжит работу (Sonnet/Haiku). Цель документа: чтобы на
каждом шаге было ясно, **что делать, как проверить и когда остановиться**.
Составлен 01-10-2026, после ревью концепции (README, «Ревью концепции»).

Прочитай перед началом: `AGENTS.md` (правила работы с владельцем действуют и
здесь), `vc-wasm/README.md`, этот файл целиком, `vc-wasm/src/rt.wat`,
`vc-wasm/src/vcsub1.wat` (образец перевода).

## 0. Главное правило: архитектура — только с владельцем

В `vc-wasm` **архитектурные решения согласуются с владельцем** (его требование
от 01-10-2026; это сильнее общего «решать самому» из `AGENTS.md`).
Архитектурное — всё, что меняет язык перевода, модель состояния, способ
переходов и вызовов, интерфейс модуля с внешним миром, источник данных,
состав инструментов сборки. Перевод **только в WAT**; другие языки как язык
перевода не используются. Если правила ниже не покрывают случай — стоп,
запись в `vc-wasm/DOUBTS.md` и вопрос владельцу, а не своё решение.

**Цель.** `vc.wasm` — Volkov Commander 4.05, переведённый моделью из
ассемблера в WAT. Тот же модуль — для запуска под WASI и для получения
нативного кода (путь — §6, не согласован).

**Не делаем** (до слова владельца): запуск программ (`EXEC`, `4B00h`) и
выгрузку VC из памяти, мышь, `VCSETUP`, VC 4.99.09, EMS, оптимизацию размера,
любые «улучшения» поведения VC.

**Решения:**

- **R1. Язык перевода — WAT.** Файлы `src/*.wat` — поля модуля без обёртки,
  `tools/build.py` склеивает их в один модуль (`rt.wat` первым).
  *Согласовано.*
- **R2. Регистры и флаги — глобальные переменные wasm** (`rt.wat`); процедура —
  функция `(param $L i32)` без результатов. *Согласовано.*
- **R3. Переходы — диспетчер по меткам**: `loop $next` + `br_table` по номеру
  метки `$L`; вход в середину процедуры — номер метки в параметре.
  *Согласовано.*
- **R4. Данные — из исходника**, в сегменты данных WAT по исходным смещениям
  (§2, A3). Бинарник `VC.COM` с модулем не поставляется; используется только
  как эталон в тестах. *Решение владельца.*
- **R5. Источник — `vc.asm` из pts-vc405-port** на коммите `PTS_COMMIT`
  (`third_party/vc/PINS`): он побайтно собирается в эталонный `VC.COM`
  (**установлено**). Адреса — из листинга JWasm.
- **R6. Эталон поведения — настоящий `VC.COM` в CPU go2dos** (харнесс, §4).
  Семантика команд и флагов в спорных местах — как в `cpu/alu.go`.
- **R7. Всё живёт в `vc-wasm/`.** Корневой модуль go2dos и его `go.mod` не
  трогать; Go-код с новыми зависимостями — во вложенном модуле
  `vc-wasm/lockstep/`.

R5–R7 и инструменты этапов A–B выбраны ревьюером по поручению владельца
(«остальное на твой выбор»); менять их — тоже через владельца.

## 1. Цикл одной сессии

1. Свежий клон `github.com/unxed/go2dos`, чтение файлов из шапки.
2. Взять первый незакрытый шаг из таблицы §7.
3. Сделать его вместе с тестами и правкой документации (§7, README «Состояние»).
4. Прогнать то, что относится к `vc-wasm` (`build.py`, `unittest`, харнесс).
   Полные наборы go2dos (`go test ./...`) — дело CI.
5. Отдать **один патч для `git am`** поверх `master`, проверив `git am` на
   свежем клоне (AGENTS.md). Размер: один шаг §7; волна перевода — 10–25
   единиц.

Логи и отчёты — компактные: одна строка на событие, не больше 20 строк
расхождений за прогон (владелец кормит логи моделям).

## 2. Этап A: листинг, единицы, данные, диспетчер

**A1. `vc-wasm/tools/listing.sh [OUTDIR]`** (по умолчанию `.cache/vc-wasm`):
вызывает `tools/build-vc405-pts.sh OUTDIR` (клонирует pts-vc405-port и
проверяет эталон), затем в `OUTDIR/pts-vc405-port`:

```sh
./tools/jwasm-2.11a.upx -q -Cp -WX -e999999999 -bin -Fo"$OUT/VC.COM" -Fl"$OUT/vc.lst" vc.asm
```

и сверяет SHA-256 `$OUT/VC.COM` с `REF_405_VC_COM` из `third_party/vc/PINS`.
**Установлено:** с `-Fl` байты `VC.COM` те же.

**A2. `vc-wasm/tools/symbols.py OUTDIR/vc.lst`** пишет (коммитятся)
`vc-wasm/data/units.json` (единицы перевода) и `vc-wasm/data/symbols.json`
(все метки и переменные с адресами, поля структур со смещениями, константы
`EQU`, если они есть в таблицах листинга).

Формат листинга (**установлено** на `vc.lst`):

- файл содержит байты ≥ 80h (строки в CP866): читать как latin-1;
- строка команды: `^([0-9A-F]{8})  ([0-9A-F]+)?\s+\t?(исходный текст)`. Адрес
  — первые 8 цифр, байты — второе поле. У некоторых строк байты не напечатаны
  (`RET` по `A48B` внутри `HexByt`): длину вычисляй как разность со следующим
  адресом;
- таблицы в конце: `Macros:`, `Structures and Unions:`,
  `Procedures, parameters and locals:` (`HexByt . . . P Near A47D _TEXT
  Public`; одна FAR: `New27 . . . P Far 04FC`), `Symbols:` (`Numb21 . . . L
  Near A470h _TEXT`);
- **установлено:** 276 процедур, 2548 меток, 1965 `CALL`, 196 `INT`; процедуры
  в `040A–CBC4`; код до `040A` (вход `Zero` по `0100`) — вне `PROC`.

**Правило единиц** (вычисляет скрипт, не исполнитель):

1. Каждая `PROC … ENDP` — единица с именем процедуры.
2. Код вне `PROC` делится на единицы по меткам, которые являются целями `CALL`,
   плюс по `0100` (`Zero`).
3. **Метки единицы** — номер 0 (вход) и далее по порядку в исходнике все
   метки внутри неё, на которые есть переход (`JMP`, `Jcc`, `LOOP`, `CALL`)
   откуда угодно. Номер метки — индекс для `$L` и `br_table`.
4. Строки данных (`DB/DW/DD`, экземпляры структур) помечаются `data` и не
   переводятся вручную (A3).

```json
{"units": [{"name": "Numb20", "start": "A467", "end": "A476", "far": false,
  "labels": ["Numb20", "Numb21"], "src": [12345, 12360],
  "callees": ["..."], "out_jumps": [["Numb21", "Numb20", 1]]}]}
```

`src` — строки `vc.asm`; `callees` — цели `CALL`; `out_jumps` — переходы
наружу: метка, единица, номер метки.

**A3. Данные — `vc-wasm/tools/gen_data.py` → `src/data.wat`** (коммитится,
вручную не правится). Для каждой метки данных — один сегмент:

```wat
;; A3F0 Country  DB 34 DUP(?)   (vc.asm:1234)
(data (i32.const 0x83F0) "\00\00…")
```

- Сегменты лежат по исходным смещениям в сегменте PSP `0800h` (линейный адрес
  `0x8000 + смещение`). Сегмент PSP 0800h — значение для будущего загрузчика
  (§6); харнесс его не использует (он копирует память целиком из go2dos).
- Байты берутся из `VC.COM`, собранного в A1, по границам из листинга; это
  разовое извлечение, источник правды после него — `data.wat`.
- Неинициализированное (`?`, `DUP(?)`) и нули не выписываются: память wasm
  обнуляется при создании.
- Печатный ASCII — как есть, остальное — `\xx`; строки CP866 — с
  транслитерацией в комментарии.
- **Тест:** байты всех сегментов `data.wat` совпадают с `VC.COM` по тем же
  смещениям; байты кода в `data.wat` не попадают.

**A4. `vc-wasm/tools/gen_dispatch.py` → `src/dispatch.wat`** (коммитится):
`(func $vc_dispatch (param $addr i32) (result i32))` — цепочка проверок адреса
входа: для переведённой единицы или её метки — вызов
`(call $X (i32.const k))` и результат 0, иначе — -1. Плюс экспорт
`(func (export "vc_call") (param i32) (result i32))`, который вызывает
`$vc_dispatch`. Список переведённых — по заголовкам `src/*.wat` (П2). После A4
временные экспорты процедур по имени в `vcsub1.wat` убрать, тесты перевести на
`vc_call`.

**A5. `vc-wasm/tools/progress.py`** печатает: всего единиц, переведено (по
заголовкам), проверено (по `vc-wasm/data/verified.txt` из харнесса).

Готово, когда: листинг воспроизводится; `units.json`, `symbols.json`,
`data.wat`, `dispatch.wat` сгенерированы; у `HexByt` вход `A47D`, у `TxtNum`
— `A4B4`; единицы и данные покрывают `0100…конец` без дыр (тест); тест данных
зелёный.

## 3. Правила перевода (П1–П16)

Образец — `src/vcsub1.wat`; все помощники — в `src/rt.wat`.

- **П1. Файлы.** Единицы из `VCxxx.INC` — в `src/vcxxx.wat`, из `VC.ASM` и
  код вне `PROC` — в `src/vc.wat` (принадлежность — по `ddanila/vc
  versions/4.05`, где стоит `PROC`).
- **П2. Заголовок единицы** — ровно так (его читают скрипты):

  ```wat
  ;; A4B4 TxtNum PROC NEAR
  ;; Вход: ES:SI.  Выход: AX, SI, DF=0.  Флаги-выход: CF.  Сохраняет: BX, DX.
  ;; Метки: 0 — вход, 1 — TxtNm1, 2 — TxtNm2, 3 — TxtNm3.
  ```

  Первая строка: `^;; ([0-9A-F]{4}) (\w+) PROC (NEAR|FAR)` (у кода вне `PROC`
  тоже `PROC NEAR`). Строка `Флаги-выход:` обязательна (П7). Номера меток —
  из `units.json`.
- **П3. Одна команда — одна-три строки WAT**, исходная команда в комментарии
  `;; MNEMONIC операнды` справа, порядок команд сохраняется. Никаких
  «улучшений» и восстановления циклов.
- **П4. Каркас функции.** `(func $Имя (param $L i32) …)`. Если у единицы есть
  метки кроме входа:

  ```wat
  (loop $next
    (block $L2
      (block $L1
        (block $L0
          (br_table $L0 $L1 $L2 (local.get $L)))
        ;; --- 0: вход
        …)
      ;; --- 1: Метка1
      …)
    ;; --- 2: Метка2
    …)
  ```

  Код метки k стоит сразу после `end` блока `$Lk`; проваливание в следующую
  метку — естественное. **Любой переход на метку k своей единицы** — только
  `(local.set $L (i32.const k)) (br $next)` (и вперёд, и назад; без «коротких
  путей»). Единица без меток — без каркаса, `$L` не используется.
- **П5. Вызовы и переходы между единицами.**
  - `CALL X` — `(call $push (i32.const 0xNEXT)) (call $X (i32.const 0))`,
    NEXT — адрес следующей команды из листинга. `CALL` на метку k другой
    единицы — то же с `(i32.const k)`.
  - `RET` — `(call $ret (i32.const 0)) (return)`; `RET n` — `(i32.const n)`;
    `RETF` — `(call $ret (i32.const 2)) (return)`; `CALL FAR` — `push` сегмента,
    `push` NEXT, вызов.
  - `JMP` на метку k другой единицы — `(call $X (i32.const k)) (return)`, без
    `push`; условный — то же внутри `(if … (then …))`.
  - Конец единицы без `RET/JMP` (проваливание в следующую) —
    `(call $Next (i32.const 0)) (return)`.
- **П6. Косвенные `CALL/JMP`** (`CALL DS:FncAddr`, `JMP [BX+tbl]`):
  `(call $push (i32.const 0xNEXT))` (только для `CALL`), затем
  `(if (call $vc_dispatch адрес) (then (unreachable)))`. Дальний вызов в чужой
  сегмент (`Country.CaseMap` — подпрограмма DOS) — `(call $vc_far seg off)`
  (импорт, §4).
- **П7. Флаги.** Вычисляй флаг только там, где его читают, прежде чем
  перезаписать: `Jcc`, `ADC/SBB`, `RCL/RCR`, `CMC`, `LAHF`, `PUSHF`, `LOOPZ`, и
  **вызывающий после возврата**. Выходные флаги единицы: для каждой точки `CALL`
  на неё смотри команды после возврата до первой, которая перезаписывает флаг;
  читаемые там флаги — выход (`Флаги-выход:`), их ставит `$setf` перед каждым
  выходом. Сравнение+переход — прямо на операндах: `CMP AX,BX / JB L` —
  `(if (i32.lt_u (global.get $ax) (global.get $bx)) (then …))`; знаковые
  (`JL/JG/JLE/JGE`) — через `i32.extend16_s`/`i32.extend8_s` и `lt_s`.
  **Ловушки 8086:** `INC/DEC` не меняют CF; `MOV`, `LEA`, `XCHG`, `PUSH/POP`
  флаги не трогают; сдвиг на 0 флаги не меняет. Сомнения — читать `cpu/alu.go`.
- **П8. Память** — только `$rb/$wb/$rw/$ww` с явным сегментом. По умолчанию —
  DS; с `BP` в адресе — SS; префикс — как в исходнике. Смещения и константы —
  числами с именем в комментарии (`(i32.const 0xA3F2) ;; Country.Sep1000`).
  **Сверка с байтами:** число должно совпасть со смещением в байтах команды
  из листинга; не совпало — ошибка адресации.
- **П9. Регистры** — глобальные `$ax…$ds`, `$flags`; значение всегда
  `0..FFFFh`: результат арифметики маскируй `(i32.and … (i32.const 0xFFFF))`.
  Половинки — `$al`/`$set_al` и т.п.
- **П10. Сдвиги и вращения на CL.** Счётчик у 8086 не маскируется, а `shl/shr`
  wasm берут его по модулю 32: для счётчика из CL добавь в `rt.wat` помощники
  с тестами (`$shl8`, `$shr16`, `$rol8` …), дающие 0 (или правильный результат
  вращения) при счётчике ≥ ширины.
- **П11. Строковые команды** — только помощниками `rt.wat` (`$stosb`,
  `$lodsb` …), они учитывают DF. Недостающие (`MOVS`, `CMPS`, `SCAS`, `REP*`)
  добавь туда по образцу, с тестами: `REP` — цикл по CX до 0.
- **П12. `INT n`** — `(call $vc_int (i32.const n))` (импорт, §4).
- **П13. `MUL/DIV/IDIV`** — DX:AX как у 8086 (образец — `MUL` в `TxtNum`);
  деление на ноль и переполнение частного — `(unreachable)`. Сработало — стоп
  (П16).
- **П14. `PUSHF/POPF`, `LAHF/SAHF`, `CLI/STI`** — через `$flags`.
- **П15. Не переводить** `VCSETUP.ASM` и единицы, достижимые только из `EXEC`
  и выгрузки (`Exec*`, `LoadOvl*`, `New27`): тело — `(unreachable)` с
  комментарием `не переводится: EXEC (PLAN §0)`.
- **П16. Стоп-условия** (не обходить; запись в `vc-wasm/DOUBTS.md`:
  установлено, не установлено, как узнать — и патч с этой записью):
  исполнение записанных программой байтов; чтение кода как данных; чтение или
  подмена своего адреса возврата; косвенный переход на адрес, которого нет в
  `units.json`; `IN/OUT`; срабатывание `(unreachable)` из П13; любое
  расхождение харнесса, причину которого не установили за 3 шага; любой
  случай, где нужно новое правило перевода (§0).

## 4. Этап B: харнесс «сверка по процедурам»

Идея: настоящий `VC.COM` работает в go2dos по сценарию клавиш. На входе в
переведённую единицу харнесс снимает состояние, дожидается возврата в
оригинале, потом прогоняет перевод из того же состояния и сравнивает.

**Где.** `vc-wasm/lockstep/` — вложенный Go-модуль (R7):

```
module github.com/unxed/go2dos/vc-wasm/lockstep
require github.com/unxed/go2dos v0.0.0
replace github.com/unxed/go2dos => ../..
require github.com/tetratelabs/wazero <последняя>
```

**Импорты модуля** — файл `src/host.wat` (модуль `vc`): `int (param i32)`,
`far (param i32 i32)`, `missing (param i32)` (`$vc_dispatch` вызывает его
перед возвратом -1, чтобы харнесс знал, кто не переведён). Тестам Python
нужны те же импорты — заглушки в `tests/vcmod.py`.

**API go2dos** (**установлено** по коду, проверить на шаге B1):
`machine.New(machine.Config{Drives: map[byte]string{'C': dir}, Codepage: 437})`,
`m.Load(`C:\VC.COM`, "")`, `m.RunScript(ctx, steps, machine.ScriptOptions{})`
(образец — `e2e/vc_test.go`). `m.CPU` — `*cpu.CPU` с полями
`BreakAt map[uint32]bool` (ключ `CS<<16|IP`) и `Break func(*cpu.CPU)`;
`machine.New` ставит их сам только при непустом `Config.Break` — не передавай
его, ставь свои после `New`. Память — `m.Mem.Read8/Write8` (линейный адрес).
Регистры wasm — экспортированные глобальные (`ax` … `flags`), wazero даёт их
как `api.MutableGlobal`.

**Шаги:**

- **B1.** Проверить на `HexByt` (`A47D`), что `Break` срабатывает **до**
  исполнения команды по адресу и что из колбэка читаются регистры и память.
  Если нет — стоп (П16).
- **B2.** Режим покрытия: `BreakAt` на все входы единиц, счётчик попаданий →
  `vc-wasm/data/coverage-<сценарий>.txt` (`адрес имя число`).
- **B3.** Режим сверки (алгоритм ниже) → `data/verified.txt` (единицы, у
  которых не меньше 5 проверенных вызовов, или все, если вызовов меньше, и ни
  одного расхождения) и сводка в stdout.
- **B4.** Статистика `INT`: `(n, AH)` и число вызовов →
  `data/int-usage-<сценарий>.txt` (нужна для решения по §6).

**Алгоритм сверки:**

1. Вход в единицу E (адрес в `BreakAt`, CS = сегмент PSP VC из
   `m.CPU.S[cpu.CS].Sel` после `Load`): снять регистры и память (1 МиБ) — S0;
   запомнить SP0 и адрес возврата по `SS:SP0`. Вложенные кадры — стеком.
2. Пока кадр открыт, на каждой команде `INT` (адреса — из листинга; в
   `BreakAt` адрес `INT` и адрес следующей команды) снять регистры и память до
   и после, записать `{n, regs_in, regs_out, diff}`. Повторное срабатывание на
   том же `INT` до возврата (ожидание клавиши, `cpu.ErrRetry`) — тот же вызов.
3. Возврат: CS:IP равен адресу возврата и `SP > SP0` — снять S1.
4. Перевод: S0 в память wasm (с адреса 0), регистры — в глобальные, вызов
   `vc_call(E)`. Импорт `vc.int` берёт следующую запись: сверяет `n` и регистры
   AX BX CX DX SI DI BP DS ES с `regs_in` (не совпало — «разошлось до INT n»),
   применяет `regs_out` и `diff`. `vc.missing(addr)` — кадр «заблокирован:
   <имя>» (не ошибка).
5. Сравнение с S1: все регистры (включая SP, SS, DS, ES); флаги — только из
   `Флаги-выход:` (харнесс читает заголовки `src/*.wat`); память — вся, кроме
   `0000–04FF` (IVT и BDA меняют прерывания таймера) и 1 КиБ под конечным SP
   в SS (мёртвая область стека).
6. Выборка: на единицу первые 10 вызовов и каждый 50-й, не больше 50 за прогон.
7. Отчёт об ошибке — одна строка: единица, номер вызова, первые 4 различия
   (`AX 1234!=1235`, `mem 0156:0A10 41!=42`).

Сценарии — скрипты клавиш пакета `keys/` в `vc-wasm/lockstep/scenarios/`,
диск C: — временный каталог с несколькими файлами (как в `e2e/vc_test.go`).
**S1**: старт, ждать `10Quit`, `Down` ×3, `Tab`, `Down`, `F10`, подтверждение.

Готово, когда: харнесс на S1 подтверждает `HexByt`, `HexCod`, `TxtNum` (если
S1 их не вызывает — добавить действие или короткий сценарий), а намеренно
испорченный перевод (`+ 8` вместо `+ 7` в `HexCod`) даёт расхождение.

## 5. Этап C: перевод волнами

1. Множество цели — единицы из `coverage-S1.txt` (потом S2, S3 …, §7).
2. **Порядок — снизу вверх:** единица готова, если её `callees` и цели
   `out_jumps` уже переведены (косвенные вызовы не учитываются — их ловит
   `vc.missing`). Среди готовых — сначала самые частые. `tools/order.py`
   печатает следующую волну.
3. Волна: 10–25 единиц → перевод по §3 → `build.py` → тесты → харнесс →
   починка → `progress.py` → патч.
4. Проверенная единица не правится без причины, найденной харнессом.
5. Первые две волны: замерь, сколько строк asm переводится за сессию, и
   запиши в README («Трудоёмкость»).

## 6. Не согласовано — до решения владельца не начинать

- **DOS-слой и терминал** для запуска `vc.wasm` вне харнесса: где они живут
  (в модуле на WAT или в хосте) и на чём написан хост; как выводится экран и
  читаются клавиши. Входные данные для решения — `data/int-usage-S1.txt` (B4).
- **Путь wasm → натив.** Замер итерации 4 сделан через w2c2, а w2c2 порождает
  C как промежуточный шаг. Допустимо ли это, или нужен другой путь (например,
  AOT-компилятор WAMR `wamrc`, ему нужен рантайм WAMR), — вопрос владельцу.
- **Сегмент загрузки PSP** (`0800h` в A3) — окончательно вместе с DOS-слоем.

Когда этапы A–C для S1 закончены, запиши в `vc-wasm/DOUBTS.md` вопросы этого
раздела с вариантами и фактами и остановись.
