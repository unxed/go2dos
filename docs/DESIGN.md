# DOS-эмулятор на Go: дизайн-документ (концепция)

Статус: черновик v0.3. Уровень детализации: концепция, без глубоких деталей.
Что уже сделано и что нет — §13; открытые вопросы и гипотезы — `docs/DOUBTS.md`.

## 1. Цель и границы

**Цель PoC:** запустить Norton Commander (`nc.exe`, есть только бинарник) внутри
Go-приложения, с отображением как можно большего числа DOS-сервисов на API
песочницы (в первую очередь файловая система).

**Форма продукта:** Go-библиотека (эмулятор как пакеты `machine`, `cpu`, `dos`, …)
плюс демо-приложение `cmd/go2dos`, которое запускает DOS-программу в терминале
или без него (headless, для автоматизации).

**Политика тестовых программ.** Нортон Коммандер — несвободное ПО, поэтому
автоматические тесты идут на VC (BSD-2). Для NC проект готовит инфраструктуру,
чтобы владелец копии мог сам запустить его в go2dos и передать разработчикам
диагностику: трассу вызовов, дамп памяти и экрана, записанную сессию клавиш
(§16). Сам NC в репозитории и в тестах не появляется.

**Промежуточная цель — Volkov Commander.** Программа того же класса (клон NC,
real mode), но с исходниками: версии 4.05 и 4.99.09 открыты под BSD-2
(`github.com/ddanila/vc`, на ветке `build` — сборка и e2e-тесты). Когда что-то
ломается, причину можно найти в исходниках, а не выводить из поведения бинарника.

**Интеграция с хостом (входит в PoC):**
- извлечение текста, выведенного в текстовом режиме (§8);
- обмен с буфером обмена хоста (§9);
- однобайтная кодовая страница DOS — по локали хоста, с ручным override (§10).

**Задел на будущее:** полноценный DOS (настоящее ядро FreeDOS + BIOS),
DOS-экстендеры (DPMI), ускорение исполнения через JIT.

**Не цели PoC:**
- Точность по тактам, звук, графические режимы, сеть.
- Загружаемые шрифты: глифы рисует хост по Unicode.
- Protected mode / DPMI (только заложить место в архитектуре).
- JIT и транспиляция (отдельные задачи после PoC).

## 2. Принципы

1. **Малые итерации (RUP-стиль):** каждый этап даёт запускаемый результат,
   проверяемый на живой программе (VC, затем NC).
2. **Fail fast:** неизвестная инструкция, неизвестная функция INT — явная
   остановка с диагностикой, по которой причину можно установить без догадок
   (CS:IP, байты опкода или AX, хвост трассы INT).
3. **Строгий скоуп:** сомнительные места фиксируются в `docs/DOUBTS.md`
   (и в комментариях) с пометкой «проверено» / «предположение»; работа продолжается.
4. **Спорные решения — в настройки** (`Config`), по возможности.
5. **Ядро CPU и слой DOS независимы** от способа исполнения кода и друг от друга.
6. **Готовый документированный интерфейс лучше придуманного:** свой API —
   только там, где существующего нет.

## 3. Обзор архитектуры

```
 Go-приложение: Run, Screen(), клавиши, вставка
                    │
            ┌───────▼────────────────────────────────┐
            │                 Machine                │
            │  (сборка: CPU + Bus + Devices + DOS)   │
            └───────┬───────────┬───────────┬────────┘
                    │           │           │
              ┌─────▼───┐  ┌────▼────┐  ┌───▼─────────────┐
              │  CPU    │  │   Bus   │  │  Devices        │
              │Executor │◄─┤ memory, │─►│ PIC/PIT/KBC     │
              │(iface)  │  │ версии  │  │ (упрощённо)     │
              └─────┬───┘  │ страниц │  └───┬─────────────┘
                    │      └─────────┘      │
                    │ trap (HLE-вызов)      │
              ┌─────▼───────────────────────▼───────────┐
              │      Firmware/DOS layer (HLE)           │
              │  BIOS, INT 21h, загрузчик, MCB, WinOldAp│
              └─────────────────┬───────────────────────┘
                                │ интерфейс Host
              ┌─────────────────▼───────────────────────┐
              │ Host: FS, Console, Keyboard, Clock,     │
              │ Clipboard, Locale — vtui / in-memory    │
              └─────────────────────────────────────────┘
```

Пакеты:

| Пакет | Роль |
|---|---|
| `cpu` | состояние CPU, интерфейс `Executor`, интерпретатор |
| `mem` | адресное пространство, A20, счётчики записей по страницам, watchpoint'ы |
| `hle` | общее ядро HLE: реестр trap-функций, заглушки в ROM, флаги в стековом кадре, трасса |
| `bios` | HLE BIOS (INT 10h/16h/1Ah/15h), область данных BIOS, клавиатура (порт 60h, IRQ1), снимок экрана |
| `dos` | HLE DOS: загрузчик, PSP, MCB, EXEC, INT 20h/21h/2Fh, отображение каталогов хоста |
| `cp` | кодовые страницы: выбор по локали хоста, таблицы OEM ↔ Unicode |
| `keys` | имена клавиш и скан-коды, формат скриптов клавиш |
| `machine` | сборка, PIC/PIT, цикл исполнения, простой, API для встраивающего приложения, дампы |
| `cmd/go2dos` | демо-приложение: терминальный фронтенд и headless-режим |

## 4. CPU

- **Интерфейс `Executor`:** `Run(budget) (StopReason)` над общим состоянием
  `cpu.State`. Интерпретатор — первая реализация. Позднее другой бэкенд
  (JIT через wazero) подключается к тому же интерфейсу и тому же состоянию.
- **Набор инструкций:** 8086 с расширениями 80186 (как у NEC V20/V30): семантика
  8086 там, где они расходятся (`PUSH SP`, биты 12–15 FLAGS, сдвиги без маски),
  плюс `PUSHA/POPA`, `ENTER/LEAVE`, `BOUND`, `INS/OUTS`, `PUSH imm`, `IMUL imm`,
  сдвиги на imm8. 386 (префиксы 66/67) — по мере необходимости; неизвестный
  опкод — остановка (fail fast).
- **Задел под protected mode с первого дня** (дёшево, только если сразу):
  - сегментные регистры хранят кэш дескриптора (base, limit, атрибуты),
    в real mode он вычисляется из селектора;
  - адрес всегда считается как `base + offset` через один путь;
  - регистры управления (CR0 и т.п.) присутствуют в состоянии, хотя в PoC не
    используются.
- **Флаги:** в PoC вычисляются сразу. Ленивое вычисление — оптимизация после
  профилирования, тесты инструкций те же.
- **Прерывания:** единый путь доставки через таблицу векторов в эмулируемой
  памяти (см. §7), чтобы работал и HLE, и настоящий код. Аппаратные IRQ
  принимаются на границе инструкций при IF=1.
- **Тестирование:** SingleStepTests 8088 v2 — все тесты проходят, кроме опкодов,
  которые у нас осознанно 80186 (60–6F, C0/C1, C8/C9); подогнаны измеренные
  особенности 8088 (порог DAA/DAS при AF, флаги при `AAM 0`, отрицание частного
  `IDIV` под префиксом REP, флаги в стеке при делении на ноль).

## 5. Шина и память

- Плоская память: 1 МБ + HMA, управление A20; extended/XMS — позже.
- **Все записи идут через один путь шины**, на нём — счётчик записей на
  страницу (4 КБ). В PoC у счётчика уже есть потребитель — экран: запись в
  `B8000–BFFFF` означает «экран изменился» (§8). Позже тот же счётчик служит
  инвалидации блоков JIT и отслеживанию самомодифицирующегося кода.
- **Текстовый видеобуфер — обычная RAM**, без MMIO-хуков: программа пишет туда,
  экран читается оттуда. Общие MMIO-хуки понадобятся с графикой (VGA planar) —
  вне PoC.

## 6. Интерфейс песочницы (Host)

Всё, что выходит за пределы эмулятора, идёт только через интерфейсы `host`:

- **FS:** операции над файлами и каталогами (open/read/write/seek, stat, readdir,
  mkdir/rename/remove). Диски DOS (`A:`, `C:` …) — это маппинг на корни
  песочницы. Отдельные вопросы: 8.3 ↔ длинные имена, регистр, атрибуты,
  путь «текущий каталог на диск». Имена: UTF-8 хоста ↔ кодовая страница DOS
  (§10); имя с символами вне кодовой страницы DOS видит как 8.3-алиас.
- **Console:** показывает снимок текстового экрана (§8): ячейки, курсор, размер.
- **Keyboard:** события клавиш со scancode, Unicode-символом и состоянием
  Shift/Ctrl/Alt (нужно для BIOS-области данных).
- **Clock:** время и дата.
- **Clipboard:** `GetText()` / `SetText()`, Unicode-текст (§9).
- **Locale:** подсказка для выбора кодовой страницы (§10).
- Реализации. Первая итерация: ФС — напрямую через `os` в пакете `dos`
  (тесты — во временных каталогах), консоль — простой ANSI-терминал на
  `golang.org/x/term`. Интерфейсы выделяются, когда появится вторая реализация:
  следующим идёт фронтенд на `vtui` (буфер обмена — тонкая обёртка над
  `vtui.SetClipboard`/`GetClipboard`, где уже есть OS-хелперы, расширения
  far2l, OSC 52 и внутренний буфер; там же — полноценные события клавиш).

Все конкретные нюансы маппинга (регистр, 8.3, атрибуты) выносятся в `Config`.

## 7. Слой DOS/BIOS: HLE с заделом под «полный DOS»

**Ключевая идея:** HLE-сервисы реализуются как **trap-функции**, а не как
«перехват в интерпретаторе». Для каждого вектора прерывания в таблице
векторов (IVT) в эмулируемой памяти записывается адрес маленькой
заглушки в области «ROM». Заглушка — специальная инструкция/опкод, которую
CPU распознаёт и передаёт вызов Go-обработчику (по аналогии с callbacks DOSBox),
после чего возвращает управление обычным `IRET`. Результат во флагах (CF и
прочие) обработчик пишет в копию FLAGS в стековом кадре — иначе `IRET` его
затрёт.

Следствия:
- Программа видит нормальную IVT и может сама перехватывать и цепочкой вызывать
  прерывания (TSR, `INT 21h/35h/25h`) — NC такое использует.
- Каждый вектор можно **независимо** отдать либо HLE (Go), либо настоящему коду.
- Переход к «полному DOS» — это смена профиля, а не переписывание:

| Профиль (`Config.Mode`) | Что делает HLE | Что исполняется как код |
|---|---|---|
| `hle` (PoC) | BIOS + вся DOS | только пользовательские программы |
| `hybrid` | BIOS и низкоуровневые устройства | настоящее ядро FreeDOS + его INT 21h |
| `full` | минимум (тонкий BIOS или настоящий) | ядро, COMMAND.COM, драйверы |

Для `hybrid`/`full` добавляется слой блочных устройств (INT 13h → образ диска
или каталог, представленный как FAT — решается отдельно) и устройства
PIC/PIT/KBC/RTC на уровне портов. В PoC эти устройства проектируются, но
упрощённо.

**Время и простой.** Таймер INT 08h (18,2 Гц: счётчик `0040:006C`, цепочка в
INT 1Ch) тикает по часам хоста между квантами исполнения. Ожидание ввода не
должно занимать ядро хоста: блокирующий INT 16h/00 и функции ввода INT 21h спят
до события клавиатуры или следующего тика; INT 28h и INT 2Fh/1680h отдают квант;
серия пустых опросов INT 16h/01 и 11h после порога из `Config` тоже переводит в
сон. Опросом ждёт клавишу, например, VC (`VCKEYB.INC`).

**INT 2Fh — мультиплексор:** на запрос к неизвестному сервису регистры по
умолчанию не меняются (для проверок наличия это ответ «не установлен»), это не
повод для остановки; каждый такой ответ пишется в трассу. VC, например,
спрашивает 168Fh, 150Bh и 4300h.

**Состав HLE в PoC:** загрузчик COM/MZ, PSP, MCB-аллокатор, INT 21h (файлы,
FindFirst/Next, DTA, EXEC, память, время, `6601h` — кодовая страница),
INT 20h/27h, INT 10h/16h/1Ah, INT 33h (мышь), INT 2Fh (минимум + WinOldAp, §9),
область данных BIOS (`0040:xxxx`), LFN (`INT 21h/71xx`).

## 8. Текстовый экран и извлечение текста

Источник правды один — видеопамять плюс область данных BIOS (режим, колонки,
строки, активная страница, курсор). Перехват вывода через INT 10h/21h полного
текста не даёт: TUI-программы пишут в видеопамять напрямую (VC — в сегмент
`B800`, см. `VC.ASM`).

API машины для встраивающего приложения:

- `Screen() (TextScreen, error)` — снимок: размер, курсор, ячейки (байт символа,
  атрибут, Unicode-руна), номер версии экрана (из счётчика записей, §5);
- `TextScreen.Text()` — строки UTF-8 без хвостовых пробелов;
  `TextScreen.Region(rect)` — прямоугольный фрагмент;
- в графическом режиме — `ErrNotTextMode`.

Снимок берётся между квантами исполнения, поэтому гонок с CPU нет. После кванта,
если версия экрана изменилась, машина передаёт снимок в `Console`. Один и тот же
снимок служит отрисовке, тестам (проверки по тексту экрана, §12) и копированию
с экрана в буфер обмена (§9).

Перевод в Unicode: байты `00–1F` и `7F` в видеопамяти — это глифы (☺ ☻ ♥ … ⌂),
а не управляющие символы; `80–FF` — по кодовой странице (§10). В файлах и
буфере обмена эти же байты — обычные управляющие символы.

## 9. Буфер обмена

**Что уже существует (проверено):**
- DOS-API буфера обмена есть: WinOldAp из Windows 3.x/9x,
  `INT 2Fh AX=17xxh` (Ralf Brown's Interrupt List). Клиенты: GNU Emacs для
  MS-DOS (`w16select.c`), `CLIP:` в 4DOS, утилита WCLIP.
- DOSBox-X пробрасывает этот API в буфер обмена хоста (Windows, Linux, macOS);
  дополнительно у него есть своё устройство `CLIP$`.
- VC 4.05/4.99.09 буфер обмена не использует: вызовов `INT 2Fh/17xxh` в
  исходниках нет. Использует ли его NC — не установлено, покажет трасса INT 2Fh
  на M5.

**Решение:** свой API не придумываем. Эмулятор реализует WinOldAp, а в VC
добавляется его клиент.

**Сервер в эмуляторе (`dos`, INT 2Fh):**
- `1700h` наличие/версия, `1701h` open, `1702h` empty, `1703h` set,
  `1704h` size, `1705h` get, `1708h` close, `1709h` compact (no-op);
  прочие функции группы — fail fast.
- Форматы `CF_TEXT` (1) и `CF_OEMTEXT` (7) ↔ Unicode через кодовую страницу
  (§10); остальные форматы — отказ (`AX=0`).
- `CLIP$` не делаем, пока нет потребителя.

**Во фронтенде (работает с любой программой, включая NC):**
- копирование: прямоугольник из снимка экрана (§8) → `Host.Clipboard`;
- вставка: текст → нажатия клавиш в буфер клавиатуры BIOS (символ → байт
  кодовой страницы, перевод строки → Enter), порциями: буфер BIOS вмещает
  15 нажатий.

**Клиент в VC** — в нашей сопровождаемой сборке VC (§18). Минимум: скопировать
командную строку или имя под курсором, вставить в командную строку; клавиши —
по конвенциям VC. Сначала 4.05 (последний полностью рабочий релиз), затем
4.99.09; изменения предлагаются и в `ddanila/vc`. Проверка — в нашем
эмуляторе и независимо в DOSBox-X (`dos clipboard api = true`), чтобы клиент и
сервер не проверялись только друг другом.

**Не установлено:** какую кодировку DOS-программы на деле кладут в `CF_TEXT`
(в Windows это ANSI-кодировка) и в `CF_OEMTEXT`. До проверки по клиентам (Emacs,
4DOS) и исходникам DOSBox-X оба формата трактуются как OEM — это предположение,
оно в `DOUBTS.md`.

## 10. Кодовая страница

На машину — одна однобайтная OEM-кодовая страница. Порядок выбора:

1. `Config.Codepage`, если задан явно (например, `866`);
2. иначе OEM-страница хоста по библиотеке `github.com/unxed/localecp`: на
   Windows — номер (`GetOEMCP`, с поправкой на UTF-8-системы), на Unix/macOS —
   по `LC_ALL`/`LC_CTYPE`/`LANG`;
3. если для страницы хоста нет DOS-таблицы — 437 с предупреждением.

Таблицы есть для 437, 850, 852, 855, 858, 860, 862, 863, 865, 866
(`golang.org/x/text/encoding/charmap`).

Override нужен, когда программа рассчитана не на ту страницу, что у хоста
(русская программа на хосте с `en_US`, и наоборот).

Перекодировка живёт в одном месте — пакете `cp`; им пользуются снимок экрана
(§8), клавиатура (символ хоста → байт в AL, scancode — из события хоста), имена
файлов (§6) и буфер обмена (§9). Программам DOS страница сообщается через
`INT 21h/6601h`.

## 11. Исполнение и ускорение (вне PoC)

| Путь | Статус |
|---|---|
| **A.** Интерпретатор на Go | PoC |
| **B1.** Трансляция x86 → wasm в рантайме (JIT), исполнение через wazero | M13, использует A как эталон |
| **B2.** Трансляция заранее (AOT) по списку блоков: из метаданных ассемблера (VC через JWasm, HX, DN через вывод компилятора Pascal) или из покрытия прогонов интерпретатора | M13 |
| **B3.** Статическая трансляция без подсказок + wasm2go | не планируется (код и данные в `.exe` не разделяются, оверлеи, косвенные переходы) |

B1 и B2 — один транслятор и одно смешанное исполнение. Блоки работают над
общим `cpu.State` и памятью, а всё непокрытое, изменённое или перемещённое
(по счётчикам записей страниц, §5) исполняет интерпретатор. Между уровнями —
платформенный ABI (HLE), поэтому сопровождаемая программа может поставляться
как `VC.wasm` с хостом HLE. Бэкенд wasm в JWasm не пишем: от ассемблера нужны
только метаданные. Подробности и план T0–T5 — `docs/TRANSLATION.md`.

## 12. Тестирование

- Юнит: инструкции (SingleStepTests, `tools/fetch-sst.sh`, отдельная задача CI
  с кешем), ALU/флаги, декодер; 8.3-имена и пути; скрипты клавиш.
- Интеграция: тестовые `.COM` (`testdata/progs`, исходники для nasm рядом);
  проверки — по снимку экрана (§8) и коду возврата.
- Сквозной: VC (`e2e/`, бинарники качает `tools/fetch-vc.sh` с проверкой
  SHA-256) — «запустился → показал каталог → вошёл в каталог → вышел»,
  проверки по `Screen().Text()`. Сценарии пишутся скриптом клавиш с
  `<waitfor:текст>`, без пауз по времени. Готовые сценарии и эталонные экраны —
  ещё в e2e-наборе VC (ветка `build`: kvikdos и QEMU). NC — у владельца копии (§16).
- Буфер обмена: сервер — тестовым `.COM` и WCLIP; клиент в VC — ещё и в DOSBox-X.
- Дифференциальный (позже): JIT против интерпретатора; экраны против DOSBox-X.
- Логирование: трассировка INT-вызовов компактная, включается в `Config`.

## 14. Риски и открытые вопросы

1. **Версия и режим NC не подтверждены** (real mode 4.0/5.x или 32-битный).
   От этого зависит набор инструкций на M1 и нужность DPMI раньше срока.
   Устанавливается до M1 по самому `nc.exe` (заголовок MZ, сигнатуры
   DOS-экстендеров).
2. **Лицензии:** DOSBox и FreeDOS — GPL-2, kvikdos — GPL ≥ 2: референс
   семантики, заимствование кода — отдельное решение (влияет на лицензию
   проекта). VC — BSD-2: читать, заимствовать и патчить можно.
3. **BIOS для режимов `hybrid`/`full`:** свой минимальный HLE или готовый
   open-source BIOS — не решено.
4. **Блочные устройства для `full`:** как представлять каталог песочницы на
   уровне INT 13h (FAT-образ на лету или образ-файл) — не решено.
5. **Запуск команд из NC/VC:** командная строка работает через `COMSPEC`
   (VC ищет `COMSPEC=` в окружении), значит, нужен настоящий `COMMAND.COM`
   (например, FreeCOM) как отдельная программа внутри эмулятора. EXEC,
   наследование хэндлов и возврат в родителя уже есть (M6).
6. **Оверлеи и самомодифицирующийся код** (у VC 4.99.09 есть оверлей `VC.OVL`):
   влияют на будущий JIT, не на PoC.
7. **Кодировка `CF_TEXT`/`CF_OEMTEXT`** у реальных клиентов — §9.

## 15. Настройки

Сейчас (`machine.Config` и флаги `go2dos`):

- диски: `-drive C=DIR` (по умолчанию — каталог программы как `C:`);
- `-cp N` — кодовая страница (0 — по хосту);
- `-trace FILE`, `-trace-filter int21,int10` — трасса HLE-вызовов (JSON lines);
- `-watch ADDR,...` — логировать записи по линейным адресам и инструкцию-автора;
- `-keys СКРИПТ` или `-keys @ФАЙЛ`, `-record ФАЙЛ` — скрипт клавиш и запись сессии;
- `-headless`, `-timeout`, `-screen-out ФАЙЛ`, `-dump-dir`, `-dump-on-exit`;
- `IdlePolls` — порог пустых опросов клавиатуры до «простоя».

Кандидаты на потом: `Mode` (`hle`/`hybrid`/`full`), правила регистра и алиасов,
буфер обмена (WinOldAp, вставка нажатиями), размер памяти и HMA.

## 16. Диагностика и тестирование NC у владельца копии

Цель: прислать разработчикам всё, что нужно, чтобы установить причину сбоя без
догадок и без доступа к самой программе.

- **Fail fast с дампом.** Неизвестная инструкция или функция — остановка и
  каталог `go2dos-dump-ДАТА/`: `report.txt` (регистры, байты по CS:IP, стек,
  последние 256 HLE-вызовов, последние адреса исполнения), `memory.bin`
  (вся память, линейные адреса — под `ndisasm`), `screen.txt`/`screen.ans`,
  `trace.jsonl`, `keys.txt`. Дамп можно снять и вручную (`Ctrl-]` `d`) или
  при любом выходе (`-dump-on-exit`).
- **Воспроизводимость.** Все нажатия пишутся как скрипт клавиш (`keys.txt`,
  `-record`); его можно проиграть (`-keys @keys.txt`), в том числе headless.
- **Инструменты расследования.** `-trace` с фильтром, `-watch` (кто пишет по
  адресу), кольцо адресов исполнения. Код пишется только для сбора информации,
  пока причина не установлена.
- Пошаговая инструкция с одним блоком для терминала — `docs/NC-TESTING.md`.

## 17. Опыт cpmulator (skx/cpmulator)

Похожая задача (CP/M на Go: CPU-ядро + BDOS/BIOS в Go через ловушки). Что из
его опыта (README, DEBUGGING.md, история коммитов) учтено:

- **Неизвестный вызов — фатальная ошибка с JSON-логом** — у нас fail fast и
  трасса JSON lines, пригодная для `jq`.
- **Результаты пишутся во все регистры, которые проверяют программы**: у них
  BDOS дублирует результат в A и HL, иначе ломались BBC BASIC и HiSoft C. У нас
  флаги результата пишутся в стековый кадр, коды ошибок — по документации.
- **Ввод для тестов «подкладывается» в эмулятор** (`*.in`/`*.pat`); у них были
  проблемы с таймингом (`#` = пауза в 1 с, чинили тест таймаута). У нас скрипт
  клавиш ждёт текста на экране (`<waitfor:…>`), а не времени.
- **Отключение эха через `stty` оказалось непереносимым** — у нас сразу
  `golang.org/x/term` (Unix и Windows).
- **Ctrl-C перезагружал CCP случайно** — у нас служебная клавиша `Ctrl-]`, редкая
  в DOS-программах, и сама передаётся программе двойным нажатием.
- **Внешний корпус программ хранится отдельно от репозитория** (`cpm-dist`) —
  у нас скрипты загрузки с проверкой контрольных сумм.
- **Нельзя менять структуры, переданные программой, сверх документированного**
  (у них — FCB при открытии файла).
- Отображение «дисков» на каталоги хоста — так же; адреса служебных областей —
  настраиваемые.

## 18. Сопровождаемые сборки DOS-программ

Продвинутые API (буфер обмена, LFN, UTF-8 имена) должны поддерживаться и в
самих программах, если там их нет. Пока всё в одном репозитории, доработанная
копия VC будет жить рядом с эмулятором (`third_party/vc`, BSD-2: исходник,
скрипт сборки, тесты); в текущей версии её ещё нет.

Проверено по исходникам:

| | VC 4.05 | VC 4.99.09 |
|---|---|---|
| LFN (`INT 21h/71xx`) | нет | есть |
| Буфер обмена (WinOldAp) | нет | нет |
| Сборка | TASM (в CI `ddanila/vc` — через QEMU) | TASM; `VC.COM` также JWasm нативно |

Порядок: буфер обмена в 4.05 и 4.99.09; LFN в 4.05; UTF-8 имена (§19) в обе.
Изменения предлагаются и в `ddanila/vc`.

## 19. UTF-8 имена файлов

Готового DOS API нет. В обсуждении DOSLFN (форум BTTR) предлагали «UTF-8 как
отдельную кодовую страницу» и сами отметили её минусы: она глобальная, ломает
программы, которые о ней не знают, и переполняет буферы.

Решение: **per-process opt-in** поверх LFN API, обнаружение через AMIS
(`INT 2Dh`, стандарт бесконфликтных расширений). Программа, которая знает про
UTF-8, включает режим для себя одной; все функции DOS с именами файлов (и 8.3,
и `71xx`) для неё принимают и возвращают UTF-8; короткие имена в этом режиме —
только ASCII. Остальные программы, включая запущенных ею детей, ничего не
замечают. Клиенту нужно только два изменения: включить режим и при выводе на
экран переводить UTF-8 в экранную кодовую страницу (ширину считать в символах).
Реализуемо везде, где есть LFN: в эмуляторах с ФС хоста (go2dos, DOSBox-X) — по
построению, в DOSLFN — UTF-16 → UTF-8 вместо UTF-16 → OEM.

Спека — `docs/UTF8NAMES.md` (на английском, для других реализаций). Ввод с
клавиатуры остаётся в однобайтной кодировке. Мост к WASI (§21) этот API не
заменяет: оба остаются.

## 20. Дальние планы

Исследование границ применимости стека и одновременно музей двухпанельников —
не просто запускаемых, а пригодных для работы.

1. **Dos Navigator.** Доработать под наши API (буфер обмена, LFN, UTF-8 имена)
   и запускать в go2dos. Юридический статус исходников DN и Turbo Vision не
   выяснен, поэтому в репозитории — только скрипты: скачать исходники (например,
   из Веб-архива), наложить наши патчи, собрать на машине пользователя.
   Компилятор выбирается по факту: что DN требует и что можно скачать и
   запустить (кандидаты — Borland/Turbo Pascal 7 внутри go2dos, Virtual Pascal,
   Free Pascal с целью i8086-msdos и Free Vision). Проверить до начала работ.
   Перед доработкой — полный аудит кода DN на совпадения 1:1 с Turbo Vision
   из Turbo Pascal: найденное переписывается с нуля по протоколу «чистой
   комнаты» и дважды перепроверяется разными способами. Затем доработанная и
   уже чистая Turbo Vision выносится в отдельный проект: обратно совместимый с
   паскалевской TV, с расширениями DN, которые подключаются отдельно, со сборкой
   во Free Pascal. Этапы D1–D7 и протоколы — `docs/DN-PLAN.md`.
2. **Norton Commander.** Дизассемблировать и добавить те же API. В репозитории —
   только патч поверх версии из Веб-архива и скрипты: скачать, сверить
   контрольную сумму, применить, проверить в go2dos.
3. **HX DOS Extender (HX DPMI).** HX запускает Win32-программы (PE) под DOS
   через DPMI и эмулирует подмножество Windows API. Если его Win32-слой
   опирается на наши API, всё, что под ним работает, получает их без
   изменений в самих программах. Пример — Far Manager для Windows: по словам
   владельца, под HX запускалась как минимум одна его версия; какая — проверить.
   С нашими изменениями он увидит длинные UTF-8 имена и буфер обмена хоста.
   - Соответствие API: Win32 `...W`-функции с именами (`CreateFileW`,
     `FindFirstFileW` и др.) переводят UTF-16 ↔ UTF-8 и идут через UTF-8 имена
     (§19) или мост WASI (§21); `OpenClipboard`/`GetClipboardData`/
     `SetClipboardData` — через WinOldAp (§9). `...A`-функции не меняются.
   - Предусловие в go2dos: 386 и защищённый режим плюс DPMI — либо настоящий
     HDPMI32 как код, либо HLE-хост DPMI. Это большой отдельный этап (§1, §4).
   - Исходники (установлено): форк — `github.com/unxed/HX` (вверху его истории
     `v2.24pre1`), у токена агента есть права на запись в него. Базовая часть —
     `Src`, эмуляция Win32 — `SrcEmu`, сборка через NMAKE или WMAKE
     (`HXsrc.txt`). Лицензия по `HXsrc.txt`: «freeware, Copyright 1996-2026
     Japheth» (автор JWasm); условия изменения и распространения там не
     оговорены. `WSOCK32` из сборки исключён — части модулей нет по авторским
     причинам.
   - Хранение: изменения HX живут в форке, в go2dos — только ссылка на него и
     тесты.
   - Исследовать до начала: как HX уже реализует имена файлов (LFN API или нет)
     и буфер обмена; какая версия Far работала под HX; чем собирать HX в CI.

## 21. Мост DOS → WASI

DOS-программа получает API песочницы WebAssembly (WASI preview1): файлы с
UTF-8 путями, каталоги, часы, случайные числа, аргументы. Это способ
взаимодействия с хостом, который уже поддержан почти везде. Обнаружение — через
AMIS, вызов — far call с блоком параметров. Структуры сохраняют раскладку
wasm32, указатели — far.

Решение: UTF-8 имена (§19) остаются быстрым путём для LFN-программ (VC, DN,
NC) и для реального DOS. Мост — для новых и портируемых программ, этап M11
после M10. Архитектура, ABI-набросок, план W0–W7 с исследовательскими
задачами — в `docs/WASI-BRIDGE.md`.

## 22. Экран: окно любого размера и консоль хоста

Программы рисуются в окне любого размера; для наших сборок это включено по
умолчанию. go2dos умеет работать как консольное приложение: VC запускается
прямо в bash, а вывод команд попадает в настоящий буфер терминала со
склеенными длинными строками.

Решение — разделить два канала вывода, которые в DOS и так разные: поток
(телетайп DOS/BIOS) и сетку (прямые записи в видеопамять). Режимы:
- `pipe` — потоки хоста вместо экрана;
- `console` — поток в буфер терминала, сетка в альтернативном экране только
  на время полноэкранного интерфейса;
- `grid` — как сейчас.

Размер окна передаётся через BDA и CRTC — там, где программы его и так
ищут. Наши сборки получают событие изменения размера и объявляют роль экрана
через AMIS-API `DOS-HOST/TEXTWIN`. Подробности и план S0–S6 —
`docs/SCREEN.md`.
