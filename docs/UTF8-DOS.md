# UTF-8 в DOS: проект целиком

Состояние на 2026-10-21. Здесь собрано, что сделано, кто реализует, с кем шла переписка и что
открыто. Сами интерфейсы описаны в спецификациях на английском: [UTF8NAMES.md](UTF8NAMES.md)
(имена файлов) и [UTF8CLIPBOARD.md](UTF8CLIPBOARD.md) (буфер обмена). Сводка всех расширений
go2dos — [DOS-EXTENSIONS.md](DOS-EXTENSIONS.md). Пометки: **установлено** — проверено по
первоисточнику (ссылка рядом), **предположение** — вывод без проверки.

## 1. Задача и принципы

DOS-программа видит имена файлов и текст буфера обмена в однобайтной OEM-кодовой странице. Всё, чего
в странице нет, теряется: японское имя на CP866, греческий текст из браузера в буфере.

Принципы, общие для всех частей:

1. **Режим включается на процесс.** Программа, которая знает UTF-8, включает его для себя. Остальные
   программы, включая её детей, ничего не замечают. Глобальную «кодовую страницу UTF-8» (её предлагали
   на форуме BTTR для DOSLFN) мы отвергли: она ломает программы, которые о ней не знают, и
   переполняет их буферы (DESIGN §19).
2. **Обнаружение через AMIS** (`INT 2Dh`), а не через новые номера прерываний: AMIS для того и
   создан, чтобы расширения не сталкивались. Производитель `DOS-UTF8`, продукты `NAMES   ` и
   `CLIPBRD `, функции `AL=10h` (установить: `BX=65001` или `0`) и `AL=11h` (прочитать).
3. **Существующие API не меняются по форме.** Имена ходят через LFN (`INT 21h/71xx`), буфер — через
   WinOldAp (`INT 2Fh/17xx`). В режиме UTF-8 меняются только байты на проводе. Новых форматов
   буфера нет.
4. **Остальное остаётся в OEM:** экран, клавиатура, окружение, командные строки. Клиент сам
   переводит UTF-8 в экранную кодовую страницу.
5. **Маленькое расширение, которое реализуемо везде:** в эмуляторе, в TSR, в DOSLFN, в
   DOS-расширителе.

## 2. Части и их состояние

| Часть | Спецификация | Состояние |

| UTF-8 текст буфера обмена, `DOS-UTF8/CLIPBRD` 1.0 | [UTF8CLIPBOARD.md](UTF8CLIPBOARD.md) | go2dos (`dos/utf8clip.go`), DOSBox-X (PR 6632) |

Расхождение реализаций в последней строке (**установлено** по описанию PR 6632): для процессов
без режима UTF-8 DOSBox-X показывает символы вне кодовой страницы как `{U+XXXX}`, а go2dos даёт
алиас (`NAMES.md`). Спецификация UTF8NAMES этот случай не регулирует, и оба поведения допустимы.

### 4.3. vbados — письмо Javier (автору vbados)

2026-10-09 предложено: TSR общего буфера обмена VirtualBox для DOS поверх vbados (HGCM
`VBoxSharedClipboard` ↔ WinOldAp `INT 2Fh/17xx`) с режимом UTF-8 через `DOS-UTF8/CLIPBRD`. Заданы
вопросы: делать внутри vbados или отдельно, и примет ли автор код, написанный с ИИ.

Ответ (2026-10-11):

- большие порции кода, написанного ИИ, сейчас не принимает; это и так выглядит отдельным
  инструментом;
- спросил, какие программы вообще используют эти функции: у себя он нашёл только 4DOS;
- считает, что пользы меньше, чем проблем, и ссылается на
  https://github.com/joncampbell123/dosbox-x/issues/5025.

Что в #5025 (**установлено** по тикету): ответ на `INT 2Fh AX=1700h` значит для программы «я в
DOS-окне Windows». Norton Desktop 1.0 и утилиты Norton Commander после такого ответа выключают свой
шрифт и графический курсор мыши. DOSBox-X держит список имён программ, которым на 1700h не
отвечает, а его сопровождающий спросил, нельзя ли дать буфер обмена так, чтобы программы не
считали себя запущенными под Windows.

Выводы:

1. VBCLIP — отдельный проект. Код vbados по GPL-2.0 (**установлено** по лицензии форков на GitHub;
   сам репозиторий автора на GitHub не найден) можно брать с указанием происхождения.
2. Возражение по #5025 верное и касается любого TSR, который отвечает на 1700h. Ответ на него —
   версия 1.1 `DOS-UTF8/CLIPBRD` (§5): по умолчанию TSR молчит на `INT 2Fh` и отдаёт буфер только
   через AMIS.
3. На вопрос «кто пользуется» честный ответ — немногие. Известные клиенты WinOldAp: GNU Emacs для
   MS-DOS (`w16select.c`), 4DOS (`CLIP:`), WCLIP; новые — наши tv3, DN и fpide, сборка VC. Главная
   польза — для своих программ.

Черновик ответа лежит вне репозитория.

## 5. Буфер обмена без WinOldAp (CLIPBRD 1.1, предложение)

Полный текст — [UTF8CLIPBOARD.md](UTF8CLIPBOARD.md), раздел «Version 1.1». Коротко:

- провайдер `DOS-UTF8/CLIPBRD` версии 1.1 принимает сами вызовы буфера: `INT 2Dh`,
  `AL = 20h + n` — то же, что `INT 2Fh AX = 1700h + n`, с теми же регистрами и результатами,
  с общим состоянием и общей кодировкой;
- поэтому ответ на `INT 2Fh AH=17h` становится необязательным: «тихий» сервер не выдаёт себя за
  Windows, и проблема #5025 не возникает;
- эмуляторам, которые уже отвечают на 1700h, рекомендуется отвечать и дальше (клиенты 1.0, Emacs,
  4DOS); новому TSR (VBCLIP) — молчать по умолчанию;
- клиенту WinOldAp нужно поменять одно место — процедуру вызова;
- совместимость: клиент 1.0 смотрит только старшую версию; против «тихого» сервера он остаётся
  без буфера, как без Windows.

Отказались от: нового формата (`CF_UNICODETEXT`, UTF-16), устройства `CLIP$`, нового номера на
`INT 2Fh`, счётчика изменений (отложен до клиента, которому он нужен).

Нужно согласование с владельцем, затем реализация в go2dos (`dos/utf8clip.go`, тест на «тихий»
режим). После этого — предложить в DOSBox-X: там же можно будет убрать список имён программ.

Цель владельца: Far 2.x или 3.x (Unicode) под HX в DOSBox-X, с длинными именами в UTF-8 и буфером

**PR из HX#75 для этого нужны, но их мало** (состояние на 2026-10-21).

Что уже есть:

- HX, PR 1 (`CP_UTF8` в `MultiByteToWideChar`/`WideCharToMultiByte`/`GetCPInfo`):
  https://github.com/Baron-von-Riedesel/HX/pull/76 (ветка `dkrnl32-cp-utf8` в `unxed/HX`, один

Чего не хватает (**установлено** разбором таблиц импорта Far 3.0.6745.5025 x86 против экспортов

### 7.2. Как дать «Far 2/3 в HX в DOSBox-X», не делая свою версию HX

Пожелание: не плодить улучшенные версии HX (и распространять изменённый HX без разрешения автора
нельзя, HX-RESEARCH §5). Поэтому HX у пользователя — официальный релиз, без наших изменений.
Варианты, от лучшего:

1. **Изменения приняты в HX.** Тогда нужен только официальный HX, официальный DOSBox-X
   (с UTF-8 провайдерами, а для Far 3 — с SSE2 или со сборкой Far без SSE2) и наш пакет настройки
   (п. 4). Это основной путь, и всё из 7.1 делается под него.
2. **Чего нет в HX, но можно сделать снаружи — делаем снаружи, не трогая HX:**
   - системные DLL, которых в HX нет вовсе (`psapi`, `secur32`, `setupapi`, `winspool.drv`,
     `imm32`, `netapi32`, `rpcrt4`, `userenv`): отдельные маленькие DLL нашего проекта с заглушками
     или простыми реализациями. Это не изменение HX, а дополнение рядом с ним;
   - функции, которых нет в DKRNL32/DUSER32: их нельзя добавить снаружи (загрузчик подставляет
     DKRNL32 вместо kernel32 по имени). Значит, программа должна сама пережить их отсутствие:
     сборка Far, которая берёт такие функции через `GetProcAddress` и умеет без них. Для Far 3 —
     предложить это в апстрим Far (у Far уже есть такой механизм для API новых Windows); для Far 2
     (больше не развивается) — наша сборка Far 2 из его исходников с этими правками;
   - префикс `\\?\`: если HX не примет исправление, сборка Far не добавляет его к путям под HX.
3. **Что живёт только внутри HX** (UTF-8 в консольных и файловых W-функциях, буфер обмена хоста):
   снаружи не сделать. Без принятия в HX остаётся только публиковать патчи к HX со сборкой у
   пользователя — и то лишь с разрешения автора (вопрос в HX#75 ещё не задан). Значит, UTF-8-часть
   цели зависит от HX upstream; это главный риск.
4. **Что публикуем в релизах** (в `unxed/go2dos` или отдельном репозитории): конфигурацию DOSBox-X,
   стартовый `.BAT`, DLL из п. 2, при необходимости — сборку Far (п. 2) и инструкцию, где взять
   официальные HX и DOSBox-X. Сам HX в наших релизах — только неизменённые официальные пакеты, если
   это вообще нужно.
5. **Far 3 и SSE2:** официальная сборка Far 3 x86 требует SSE2, а DOSBox-X его не умеет. Пути:
   SSE2 в DOSBox-X (7.1, предпочтительно — польза всем) или сборка Far 3 x86 с `/arch:IA32`
   (как временная мера — в наших релизах; в апстрим Far — только если они захотят такую сборку).

Риски:

- Japheth сам делать это не будет; примет ли он PR — неясно (§4.2). Если не примет, работа
  остаётся в форке `unxed/HX`. Но распространять изменённый HX без его разрешения нельзя
  (HX-RESEARCH §5): для своего стенда можно, для релиза — нет.
- Часть API Far нельзя сделать в DOS по существу (процессы и job objects, именованные каналы,
  тома). Заглушка должна давать отказ, с которым Far умеет жить; это покажет только стенд H2.
- Плагины: `arclite` (его `7z.dll` импортирует `msvcrt.dll`), `NetBox`, `LuaMacro` (`lua51.dll`)
  тянут свои DLL. Сначала цель — Far без плагинов или с минимальным набором.
